# 五看三定分析：Git 学习笔记 + 本地 AI 部署

> 分析对象：本项目（Git 学习笔记 + `ai-local-deploy` 本地部署方案）
> 分析方法：华为「五看三定」——先看行业/趋势、市场/客户、竞争、自己、机会，再定战略控制点、定目标、定策略
> 分析日期：2026-11-14

## 0. 一页纸结论

| 维度 | 核心判断 |
| --- | --- |
| 行业/趋势 | 开源协作是软件工程默认方式，大模型正从云端走向端侧，两者叠加是长期方向 |
| 市场/客户 | 同学、个人开发者、离线/内网环境用户，缺的是「中文、可复现、低门槛」的完整闭环 |
| 竞争 | 通用工具（Ollama、LM Studio）很强，但中文教学型、带排错与脚本的完整方案不多 |
| 自己 | 文档与脚本完整、有真实分支协作记录；缺实测性能数据与社区基础 |
| 机会 | 课程作业 → 个人作品集 → 校内分享，成本低、可复用 |
| 战略控制点 | 不是模型本身，而是「30 分钟照着文档就能跑起来」的可复现体验 |
| 目标 | 部署成功率 ≥ 90%、文档覆盖 100%、分支流程规范 100% |
| 策略 | 分支协作 + 文档驱动 + 社区互动 + 脚本化自检 |

## 1. 五看

### 1.1 看行业与趋势

- **开源成为默认协作方式**：从操作系统到 AI 模型，主流项目都以开源仓库为中心协作，Git 是事实标准。会读、会提 PR、会解决冲突已成为基本工程能力。
- **大模型从云端走向端侧**：Ollama 让 7B～32B 模型能在消费级显卡上运行，隐私、成本、离线是三大驱动力；本地推理不再是极客玩具。
- **教育场景同步变化**：课程作业从"写代码"转向"做开源项目"，要求仓库、许可证、文档、协作流程齐全。

判断：**"会部署 + 会写文档 + 会用分支协作"** 的组合，比只会调用云端 API 更有壁垒，也更适合作为课程作品。

### 1.2 看市场与客户

| 客户群体 | 核心需求 | 主要痛点 |
| --- | --- | --- |
| 同班同学 | 照着文档完成作业、少踩坑 | 环境配置、模型选型、报错看不懂 |
| 个人开发者 | 本地跑模型、接自己的应用 | 教程碎片化，Docker / 驱动门槛高 |
| 离线/内网用户 | 数据不出本机、断网可用 | 云端方案不可用，缺可复现的离线部署包 |
| 初学者 | 快速体验、建立信心 | 首次加载慢、显存不足直接劝退 |

需求共性：**开箱即用、中文说明、每一步都能验证**。价格不是主要门槛，时间成本才是。

### 1.3 看竞争

| 竞品/替代方案 | 优势 | 对本项目的启示 |
| --- | --- | --- |
| 云端 API（OpenAI 等） | 效果强、免部署、按量付费 | 本地方案要主打隐私、离线、零调用成本，而不是"更强" |
| Ollama 官方文档 | 权威、更新快 | 不重复造轮子，聚焦中文场景与排错整合 |
| LM Studio | 图形界面、零命令行 | 本项目保留 Docker 一键编排，降低命令行门槛 |
| llama.cpp / vLLM | 性能与可控性 | 通过文档说明何时该换方案，而不是自己实现推理 |
| 同学同类项目 | 同起点、同评分标准 | 差异化在「完整闭环 + 真实冲突记录 + 五看三定」 |

判断：不与通用工具拼功能，拼的是**中文、教学向、可复现的整合质量**。

### 1.4 看自己

**优势**

- 文档完整：部署 5 篇 + 分支实录 + 本分析，结构清晰、互相链接；
- 有可运行代码：4 个 PowerShell 脚本、3 个 Python 示例，且做了错误路径处理；
- 有真实协作痕迹：feature 分支、`--no-ff` 合并、add/add 冲突解决全过程可查；
- 有环境自检：`check-env.ps1` 能直接给出「这台机器适合跑多大模型」的结论。

**劣势**

- 单人维护，没有社区反馈与真实用户数据；
- 只有一台 RTX 4060 Laptop（8 GB）实测环境，缺多硬件对比数据；
- 只在 Windows 验证，Linux / macOS 路径未实测；
- 项目定位偏教学，工程深度有限。

**资源**：一台 8 GB 显存的笔记本、课程时间、GitHub 免费仓库与 Actions 额度。

### 1.5 看机会

1. **课程作业 → 作品集**：同一份仓库既满足考核，又能放进简历与面试演示，边际成本为零。
2. **校内分享**：把部署踩坑整理成一次社团分享，反向补充文档，形成"用输出倒逼输入"。
3. **补实测数据**：不同显存/模型的速度与显存占用表格，是当前最缺、也最容易积累的差异点。
4. **扩展场景**：RAG 知识库、代码助手、离线客服，都是本地模型的高频落地点。

优先级：先补实测数据（成本低、说服力强），再做分享（扩大影响），最后考虑扩展场景。

## 2. 三定

### 2.1 定战略控制点

**控制点：可复现的部署体验。**

理由：模型能力由上游决定，本项目无法控制；但「照着 README，30 分钟内从零到能对话」这件事完全可控。它依赖三样东西：

- 文档准确（命令能直接复制执行）；
- 脚本能自检（`check-env.ps1` 先告诉你机器行不行）；
- 排错清单完整（常见问题有可执行诊断命令）。

只要这三点持续成立，项目就有独立价值，不随模型版本过时。

### 2.2 定目标

| 目标 | 指标 | 当前状态 |
| --- | --- | --- |
| 部署可复现 | 新用户按 README 30 分钟内部署成功 | 文档与脚本已就绪，待多人验证 |
| 文档覆盖 | 每个模块都有对应文档与示例 | 5 篇部署文档 + 分支实录 + 本分析，达标 |
| 协作规范 | 所有功能走 feature 分支 + `--no-ff` 合并 | 已建立并演示一次冲突解决 |
| 社区互动 | ≥ 3 条有效 Issue 讨论、≥ 10 Star | 待邀请同学参与 |
| 代码质量 | 脚本语法检查、示例可编译、链接可访问 | 已通过本地验证 |

### 2.3 定策略

1. **分支策略**：`main` 只接受合并；功能走 `feature/*`；集成用 `dev`；合并统一 `--no-ff`，冲突照 [03-branch.md](../03-branch.md) 的六步处理。
2. **文档驱动**：新增功能必须同步更新 README 与对应文档，否则不合并——文档是本项目的产品本身。
3. **社区互动**：用 Issue 模板降低提问门槛，用 [讨论议题](讨论议题.md) 主动发起话题，定期把结论回写进文档。
4. **质量保障**：提交前跑 `check-env.ps1`、`py_compile`、Markdown 链接检查，把可自动化的检查尽量自动化。

## 3. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 模型/镜像版本更新导致命令失效 | 文档逐步失真 | README 标注验证日期；优先使用稳定 tag |
| 单机实测数据不足 | 选型建议缺说服力 | 邀请 2～3 位同学在不同配置复现并回填数据 |
| 社区互动不足 | 作业要求第 4 条不达标 | 主动发起讨论议题、在班级群邀请 star/watch |
| 范围膨胀 | 精力分散、质量下降 | 本项目只做「部署 + 文档 + 协作示范」，不扩展成框架 |
