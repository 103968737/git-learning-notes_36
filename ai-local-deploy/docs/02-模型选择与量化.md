# 02 模型选择与量化

本地部署的第一个问题不是「哪个模型最强」，而是「我的显存装得下谁」。这篇给出估算方法、量化格式取舍和一份可直接照抄的模型清单。

## 1. 显存估算

一个粗略但好用的公式：

```
显存需求 ≈ 参数量(B) × 每参数字节数 + KV Cache + 运行时开销(1～2 GB)
```

其中「每参数字节数」由量化精度决定：

| 量化格式 | 每参数字节 | 7B 模型权重 | 质量损失 | 建议 |
| --- | --- | --- | --- | --- |
| F16 / BF16 | 2.0 B | ≈ 14 GB | 无 | 显存充裕、追求最高质量 |
| Q8_0 | ≈ 1.06 B | ≈ 7.5 GB | 几乎无感 | 显存富余时可选 |
| Q6_K | ≈ 0.82 B | ≈ 5.8 GB | 很小 | 与 Q5 差距不大，性价比一般 |
| **Q4_K_M** | **≈ 0.63 B** | **≈ 4.5 GB** | 小，基本无感 | **默认推荐**，速度与质量平衡 |
| Q3_K_M | ≈ 0.49 B | ≈ 3.5 GB | 可感知 | 显存实在不够时的妥协 |
| Q2_K | ≈ 0.35 B | ≈ 2.5 GB | 明显退化 | 只用于「能跑就行」 |

**KV Cache** 随上下文长度增长：7B 模型、8K 上下文大约再占 1～2 GB，32K 时可能到 6 GB 以上。`OLLAMA_NUM_PARALLEL` 调大时，每个并发都要一份 KV Cache。

> 经验值：8 GB 显存跑 7B-Q4 刚好舒适；12 GB 可以上 14B-Q4；24 GB 可上 32B-Q4。显存不足时 Ollama 会自动把部分层放到 CPU，速度会明显下降（看日志里的 `offloaded X/Y layers to GPU`）。

拉取方式：

```powershell
ollama pull qwen2.5:7b
ollama list          # 查看已下载模型与体积
ollama rm qwen2.5:1.5b   # 删除不用的模型，释放磁盘
```

## 3. 选型流程

1. **先看显存**：8 GB → 7B-Q4；12 GB → 14B-Q4；24 GB → 32B-Q4；无独显 → 1.5B～3B。
2. **再看语言**：中文为主的问答/写作优先 `qwen2.5` 系列；英文与生态兼容优先 `llama3.1`。
3. **最后看任务**：代码用 `qwen2.5-coder`，数学推理用 `deepseek-r1`，检索用 `nomic-embed-text` / `bge-m3`。
4. **先小后大**：先用 7B 把流程跑通，再换 14B/32B 对比效果；大模型不是在所有任务上都更好。

## 4. 上下文长度怎么定

- Ollama 默认按模型原生上下文（常见 8K）。可以在 WebUI 或 API 的 `options.num_ctx` 中调整。
- 上下文开得越大，KV Cache 越大、首字延迟越高。日常问答 4K～8K 足够，长文总结再上 16K～32K。
- 超长上下文在 7B 模型上效果会明显衰减，不要指望「塞进去就懂」。

## 5. 量化版本怎么选

同一个模型往往有 `Q4_K_M`、`Q5_K_M`、`Q8_0` 等多个 tag。判断方法：

1. 先看 **Q4_K_M** 能不能装进显存；
2. 装得下且显存还有 2 GB 余量 → 试 Q5/Q6；
3. 装不下 → 降参数量（14B-Q4 换成 7B-Q5，通常前者更好）；
4. 除非做评测对比，不建议选 Q2/Q3。
