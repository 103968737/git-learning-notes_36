# 03 部署方案对比

本地跑大模型不止 Ollama 一条路。这篇把常见方案的定位、优缺点和适用场景放在一张表里，方便按需求选型。

## 1. 总览

| 方案 | 定位 | 安装难度 | GPU 支持 | 并发能力 | OpenAI 兼容 | 适合谁 |
| --- | --- | --- | --- | --- | --- | --- |
| **Ollama** | 模型管理 + 推理服务 | ★☆☆☆☆ | NVIDIA / AMD / Apple | 中（单机多请求） | ✅ | 个人开发、快速验证、本项目 |
| **LM Studio** | 桌面图形化客户端 | ★☆☆☆☆ | NVIDIA / AMD / Apple | 低 | ✅（本地服务模式） | 不想碰命令行的人 |
| **llama.cpp** | 底层推理引擎 | ★★★★☆ | 广泛（CUDA/Metal/Vulkan） | 低 | ✅（server 模式） | 想精细控制量化与参数 |
| **vLLM** | 高吞吐推理服务 | ★★★☆☆ | NVIDIA 为主 | **高**（PagedAttention） | ✅ | 多人共享、生产 API |
| **LocalAI** | OpenAI 兼容网关 | ★★☆☆☆ | 依赖后端 | 中 | ✅ | 需要统一网关、多模型路由 |
| **SGLang / TGI** | 生产级推理框架 | ★★★★☆ | NVIDIA | 高 | ✅ | 团队生产环境、批量推理 |

## 2. 逐个说明

### Ollama

一条命令拉模型、一条命令起服务，自动处理量化格式、GPU 分层卸载和模型缓存。

- 优点：上手最快；模型库丰富；自带 OpenAI 兼容接口；跨 Windows/macOS/Linux。
- 缺点：并发调度简单，高并发下吞吐不如 vLLM；高级参数（KV Cache 类型、批处理）可调项少。
- 结论：**个人与小团队的首选**，也是本项目的默认方案。

### LM Studio

图形界面选模型、调参数、开本地 API 服务，适合完全不想用命令行的人。

- 优点：零命令行；内置模型搜索与下载；可直接开启 `localhost:1234` 的 OpenAI 兼容服务。
- 缺点：闭源；自动化/脚本化能力弱；批量部署不方便。
- 结论：桌面体验优先、只做本机对话时很合适。

### llama.cpp

Ollama 底层的推理引擎，直接跑 GGUF 量化模型。

- 优点：对硬件最友好（Vulkan/Metal/CPU 都能跑）；参数控制最细；启动快。
- 缺点：需要自己找 GGUF 文件、自己写启动参数；没有模型管理。
- 结论：嵌入式、老硬件、想压榨最后一点性能时使用。

### vLLM

面向生产的高吞吐推理框架，核心是 PagedAttention 与连续批处理。

- 优点：并发吞吐可达 Ollama 的数倍到数十倍；支持张量并行；生态成熟。
- 缺点：主要面向 NVIDIA；安装依赖多；显存占用更激进；对个人电脑偏重。
- 结论：**多人同时用、要做在线服务**时再上。

### LocalAI

把多种后端（llama.cpp、vLLM、Transformers）包成统一的 OpenAI 兼容 API。

- 优点：一个网关接多个模型/后端；兼容性最好。
- 缺点：配置项多；排错链路长。
- 结论：已有业务系统、需要「换模型不改代码」时考虑。

## 3. 怎么选

```text
只是自己用、想快点跑起来
  ├─ 喜欢命令行/要接脚本 → Ollama
  └─ 喜欢图形界面         → LM Studio

要给团队/多人同时用
  ├─ 有 NVIDIA 显卡、追求吞吐 → vLLM
  └─ 想少折腾、人数不多       → Ollama + Open WebUI

要在老设备/边缘设备上跑
  └─ llama.cpp + GGUF 小模型

已有系统要统一接多个模型
  └─ LocalAI / 自建网关
```

## 4. 本项目的取舍

选择 **Ollama + Open WebUI** 的原因：

1. 一条 `docker compose up -d` 就能得到「服务 + 界面」的完整闭环；
2. 模型切换只需改一个 tag，方便对比不同参数量与量化；
3. 自带 OpenAI 兼容接口，示例代码可以直接迁移到真实业务；
4. 后续要上并发，可以只把 Ollama 换成 vLLM，WebUI 与客户端代码不用动。
